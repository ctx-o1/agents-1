# agents(-1)

## Run

Requires Python 3.14+ and [uv](https://docs.astral.sh/uv/getting-started/installation/).
From this project folder, using PowerShell:

```powershell
uv sync
# On a fresh checkout, create .env once:
Copy-Item .env.example .env
```

Add your OpenRouter key to `.env`:

```dotenv
OPENROUTER_API_KEY=your-openrouter-key
OPENROUTER_MODEL=deepseek/deepseek-v4.1-flash-1017
```

Run the chat loop or a single task:

```powershell
uv run chat.py
# Or:
uv run agent.py
```

Both entry points load the project's `.env` automatically. Existing environment
variables take precedence. `.env`, `.venv/`, and `workspace/` are ignored by Git.
Running `uv sync` creates `uv.lock` with the resolved dependency versions.

The default model is `deepseek/deepseek-v4.1-flash-1017`
([DeepSeek V4.1 Flash 1017](https://openrouter.ai/deepseek/deepseek-v4.1-flash-1017)).
Override it with `OPENROUTER_MODEL`.
The agent creates `workspace/` when it starts. Example task: "Write a hello.txt
file containing Hello, world! and read it back."

For an ongoing conversation, run `uv run chat.py`. Each user message runs the
agent loop with the shared conversation history, including previous assistant
and tool messages. Type `/exit` to quit. History stays in memory until you exit.
`agent.py` still runs one task and exits.

## The agent loop

The model chooses an action, our code executes it, and the result goes back to
the model. Validation, limits, logging, and conversation history support that loop.

```text
messages = [system instructions, user task]

repeat up to MAX_ROUNDS:
    response = call model with messages and available tools

    if response was cut short or blocked:
        stop with an explanation

    append model response to messages

    if response has no tool calls:
        return model's final answer

    for each tool call in response:
        parse and validate arguments
        execute the requested tool
        capture its result or error

        append tool result to messages
        attach the matching tool-call ID

return "Maximum rounds reached"
```

Each user message allows up to 10 model rounds. `agent.py` keeps history for one
task; `chat.py` keeps it across user messages in the same session.

## Chat templates and multiple agent turns

A basic chat often follows `system -> user -> assistant -> user -> assistant`.
In an agent loop, one user message can lead to several assistant turns before
the final answer. Each turn is generated by a separate model request; the user
does not need to send another message between them. Here, "agent turn" means
one assistant response from the same model, not a different agent.

```text
system:    Instructions and available behavior
user:      Read notes.txt and save a summary
assistant: Call list_files()                     <- model request 1
tool:      notes.txt
assistant: Call read_file("notes.txt")           <- model request 2
tool:      Contents of notes.txt
assistant: Call write_file("summary.txt", ...)   <- model request 3
tool:      File written
assistant: Saved the summary to summary.txt.     <- model request 4
```

That is one user message, four assistant messages, and three tool messages.
Each request formats the accumulated transcript and prompts the model to
generate the next assistant turn. A chat template therefore needs to represent
the whole sequence, rather than assume strict user/assistant alternation.

The assistant's tool call and the tool's result are separate messages. Each
result includes a `tool_call_id` matching the assistant's call. One assistant
message can request several tools, producing several tool-result messages.

Our Python loop sends the transcript and tool definitions, executes requested
tools, and appends their results before making the next request. This version
continues when the assistant requests tools and stops when it returns an answer
without tool calls, or when the 10-round limit is reached.

With local inference, a tool-aware chat template (for example, through
`apply_chat_template()`) formats the messages and tool definitions for the model.
Here, we send structured messages through the OpenAI client; OpenRouter and the
provider handle the model-specific formatting. The exact tokens and tool
encoding depend on the model's template.
