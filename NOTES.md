
## The agent loop

The model chooses an action, our code executes it, and the result goes back to
the model. Validation, limits, logging, and conversation history support that loop.

```text
session = create or load saved session
append user task to session messages
save session

repeat up to MAX_ROUNDS:
    response = call model with instructions, saved context, messages, and tools

    if response was cut short or blocked:
        stop with an explanation

    append model response to messages
    save session

    if response has no tool calls:
        return model's final answer

    for each tool call in response:
        parse and validate arguments
        execute the requested tool
        capture its result or error

        append tool result to messages
        attach the matching tool-call ID
        save session

return "Maximum rounds reached"
```

Each user message allows up to 10 model rounds. Both entry points save history;
`chat.py` keeps accepting user messages in the current session.

## Chat templates and multiple agent turns

A basic chat often follows `system -> user -> assistant -> user -> assistant`.
In an agent loop, one user message can lead to several assistant turns before
the final answer. Each turn is generated by a separate model request; the user
does not need to send another message between them. Here, "agent turn" means
one assistant response from the same model, not a different agent.

```text
system:    Instructions and available behavior
user:      Read notes.txt and save a summary
assistant: Call list_files()                     <- model request 1
tool:      notes.txt
assistant: Call read_file("notes.txt")           <- model request 2
tool:      Contents of notes.txt
assistant: Call write_file("summary.txt", ...)   <- model request 3
tool:      File written
assistant: Saved the summary to summary.txt.     <- model request 4
```

That is one user message, four assistant messages, and three tool messages.
Each request formats the accumulated transcript and prompts the model to
generate the next assistant turn. A chat template therefore needs to represent
the whole sequence, rather than assume strict user/assistant alternation.

The assistant's tool call and the tool's result are separate messages. Each
result includes a `tool_call_id` matching the assistant's call. One assistant
message can request several tools, producing several tool-result messages.

Our Python loop sends the transcript and tool definitions, executes requested
tools, and appends their results before making the next request. This version
continues when the assistant requests tools and stops when it returns an answer
without tool calls, or when the 10-round limit is reached.

With local inference, a tool-aware chat template (for example, through
`apply_chat_template()`) formats the messages and tool definitions for the model.
Here, we send structured messages through the OpenAI client; OpenRouter and the
provider handle the model-specific formatting. The exact tokens and tool
encoding depend on the model's template.

## State limitations:

- Use one writer per project. Atomic replacement prevents partial JSON files;
  it does not provide multi-process locking or transactions across stores.
- Transcripts and notes are local plaintext and can contain private data. The
  prompt tells the agent not to save secrets in memory or scratchpads; there is
  no complete secret detector or encryption.
- Session files have a 10 MB limit. There is no context compaction yet, so the
  model's context limit can be reached earlier. Use `/new` for a fresh context.
- History search uses a case-insensitive literal substring, scans at most the
  100 most recently updated sessions, and returns at most 20 excerpts of 800
  characters. Invalid files are skipped and counted. It is not semantic search;
  a miss does not establish that no earlier discussion exists.
- History records what was said and what tools reported; old assistant claims
  and saved memories still need verification against current evidence.

## File tools

All paths are relative to `workspace/`.

| Tool | Purpose |
|---|---|
| `list_files(path=".")` | List directory entries |
| `read_file(path)` | Read a UTF-8 text file |
| `write_file(path, content)` | Create or overwrite a text file |
| `edit_file(path, old_text, new_text)` | Replace one exact, unambiguous text match |
| `search_files(pattern, path=".")` | Search recursively for a case-sensitive literal string |
| `find_files(glob, path=".")` | Find files by glob, such as `**/*.py` |

Edits support files up to 20,000 characters. Search skips binary, unreadable,
and files larger than 1 MB. Search and find results are capped at 200 entries
and bounded output. Recursive discovery skips directory symlinks and junctions;
file links resolving outside the workspace are excluded.

## Tool limitations

These tools are intended for small, trusted workspaces.

- **Filesystem protection:** resolved-path checks reject ordinary escapes from
  `workspace/`, but provide no OS sandbox. Concurrent symlink changes and hard
  links can undermine that boundary. Keep sensitive files outside the workspace.
- **Writes:** files are overwritten directly, without atomic replacement,
  backups, or locking. Interruptions can leave partial files; concurrent edits
  can be lost. Text edits may normalize line endings.
- **Text support:** file tools expect UTF-8. Reads return at most 20,000
  characters; writes and edits reject content beyond that limit. Edits require
  exactly one occurrence of the supplied text.
- **Search coverage:** search uses case-sensitive literal matching. Binary,
  unreadable, and files larger than 1 MB are silently skipped, so no matches
  does not establish that the string is absent from every file. Matching-line
  previews include only their first 500 characters.
- **Traversal cost:** recursive search and discovery have no deadline or limit
  on files visited. They scan directories before filtering file patterns and
  do not honor `.gitignore` or exclude generated directories automatically.
- **Output limits:** search and find stop at 200 results or their output limit.
  Directory listings show only the first 200 sorted entries, without a
  truncation notice, and sort the complete directory before applying that cap.
- **Validation status:** basic behavior and path checks have been exercised
  locally. Large-workspace performance and adversarial security have not been
  comprehensively tested.
